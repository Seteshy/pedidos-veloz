ROTEIRO DO PITCH — DEMONSTRAÇÃO DO PROJETO
Meta: cerca de 3 minutos e 45 segundos. Limite: 4 minutos.
Use as falas como apoio e explique com suas palavras. A apresentação percorre a arquitetura, um pedido real no ambiente de laboratório e as decisões técnicas.

O QUE DEIXAR PREPARADO
- VS Code com a pasta pedidos-veloz aberta e a prévia do README na seção Arquitetura. O explorador mostra a organização em app, db, observability, k8s, infra e .github/workflows.
- Navegador com três abas: http://localhost:8080/docs, http://localhost:9090 e http://localhost:16686.
- Uma aba com a execução aprovada do GitHub Actions: https://github.com/Seteshy/pedidos-veloz/actions/runs/45254549698.
- Docker Desktop em execução. Como o ambiente desta máquina já está configurado, não copie .env.example sobre o .env e não altere a senha durante a preparação.
- Antes de gravar, ensaie a criação de um pedido e confira as métricas e o trace. Prepare um UUID novo para o pedido da gravação. O comando [guid]::NewGuid().ToString() no PowerShell gera esse ID.
- Deixe fora da gravação o .env, .local, senhas, kubeconfig e configurações de autenticação.

0:00 A 0:50 — ARQUITETURA E CONTAINERS
Tela: README no VS Code, diagrama da arquitetura e organização das pastas. Use o README para explicar o fluxo, sem ler código linha por linha.
Fala sugerida:
“Sou Arthur Lima Pereira, estudante de Análise e Desenvolvimento de Sistemas da UNIFECAF. Este é o Pedidos Veloz, um MVP para o cenário da Loja Veloz. O cliente acessa o Gateway; Pedidos coordena a reserva no Estoque e o Pagamento simulado. Os dados ficam no PostgreSQL.
Usei Docker Compose para iniciar os serviços de forma padronizada. As aplicações compartilham uma imagem Python, mas executam como quatro serviços separados. A imagem tem build em duas etapas e usuário sem privilégios. O volume preserva os dados do banco entre recriações dos contêineres.”
Decisões cobertas: divisão dos serviços, ambiente reproduzível, imagem, usuário e persistência.

0:50 A 1:30 — AMBIENTE FUNCIONANDO
Tela: http://localhost:8080/docs.
Ação:
1. Abra POST /orders e clique em Try it out.
2. Preencha order_id com o UUID novo preparado, sku com CAMISETA, quantity com 1 e simulate_decline com false.
3. Clique em Execute e mostre a resposta com status CONFIRMED.
4. Se couber no tempo, mostre GET /orders/{order_id} com esse ID. Não é necessário demonstrar todos os casos de teste no pitch.
Fala:
“Aqui crio um pedido pela API. O serviço reserva o item, consulta o pagamento simulado e confirma o pedido. O ID também permite consultar o resultado e evita processar novamente a mesma solicitação. Se o pagamento for recusado, o fluxo implementado devolve a reserva ao estoque.”
Não é necessário abrir um terminal ou editar código durante essa demonstração.

1:30 A 2:15 — MÉTRICAS E TRACES
Tela 1: http://localhost:9090.
Ação: execute a consulta abaixo e mostre os contadores por serviço. Você pode deixá-la preenchida antes da gravação:
sum by (service) (veloz_http_requests_total)
Fala:
“O Prometheus coleta as métricas de requisições e duração. Esta consulta mostra os contadores por serviço.”
Tela 2: http://localhost:16686.
Ação: selecione gateway em Service, clique em Find Traces e abra um trace de POST /orders que mostre os quatro serviços. Os traces levam alguns segundos para aparecer; confira isso no ensaio.
Fala:
“No Jaeger, o trace acompanha a mesma requisição pelo Gateway, Pedidos, Estoque e Pagamentos. O OpenTelemetry propaga esse contexto. Os logs JSON também incluem o identificador do trace para relacionar os eventos.”
Decisões cobertas: métricas, logs e tracing distribuído. Não é necessário abrir arquivos de configuração dessas ferramentas.

2:15 A 2:55 — KUBERNETES, DEPLOY E ESCALABILIDADE
Tela: volte ao README no VS Code, nas seções Kubernetes local, Manifests e segurança e HPA. Mostre brevemente a pasta k8s. Não precisa abrir e percorrer os YAMLs.
Fala:
“No Kubernetes, os Deployments mantêm as réplicas e os Services organizam o acesso entre elas. Usei ConfigMap e Secret para separar configuração e credenciais. As probes indicam se o processo está vivo e pronto para receber tráfego.
Escolhi rolling update para substituir as réplicas gradualmente. O HPA usa CPU e varia de duas a quatro réplicas. No teste local, Gateway e Estoque aumentaram para quatro e depois voltaram a duas. Isso demonstra a escala automática no laboratório, sem comprovar capacidade de produção.”
Não execute novamente a carga de três minutos durante o pitch. Se quiser mostrar a evidência, deixe evidencias/hpa-eventos.txt e hpa-retorno.json preparados antes da gravação.

2:55 A 3:30 — PIPELINE CI/CD
Tela: execução aprovada do GitHub Actions no navegador. Mostre validar, kubernetes-laboratorio e publicar com sucesso.
Fala:
“O pipeline faz lint, testes, build, teste completo com Compose e validação Terraform. Depois implanta e testa em um cluster Kubernetes temporário. Só após as verificações publica a imagem no GHCR, identificada pelo commit.
A imagem publicada também foi testada no Kubernetes local. O deploy automático para um cluster externo permanece desabilitado. O Terraform criou o namespace do laboratório sem contratar nuvem.”
O arquivo .github/workflows/ci-cd.yml pode ser mostrado brevemente no VS Code, mas isso é opcional. A tela de execução comprova o pipeline e evita gastar o pitch lendo YAML.
